Build the backend API for the Sava partner portal PoC.

First inspect the existing API project, identify its language, framework, database, and conventions, then implement the API using those conventions. If the project is empty, choose a maintainable stack suitable for a small REST API. Include database models/migrations, validation, API documentation, seed data, and tests for the API. Keep the API separate from the Angular frontend; do not modify the frontend unless a small API client contract/document is useful.

API conventions
- Base path: /api/v1
- JSON request and response bodies, except photo upload.
- Use ISO 8601 timestamps and YYYY-MM-DD dates. Use Africa/Luanda for business date handling.
- Currency is AOA, displayed as Kz in the frontend. Store monetary values as integer AOA amounts.
- Use UUIDs for entity IDs.
- Use consistent pagination: query parameters page (default 1) and pageSize (default 20); response includes { items, page, pageSize, total }.
- Use consistent errors: { error: { code, message, details? } } with appropriate HTTP status codes.
- Validate input and return useful field-level validation errors.
- Protect partner endpoints with authentication and ensure each partner can access only their own data.
- Do not trust client-supplied prices or totals. Calculate prices and totals on the server from the property rate and dates.
- Use enums consistently in the API. Suggested reservation statuses: pending, confirmed, checked_in, completed, cancelled. Suggested listing statuses: published, draft. Suggested payment statuses: pending, processing, paid, failed, refunded.
- Include seed/demo data corresponding to the existing PoC listings and reservations.

    Public; no partner authentication.

Implementation expectations
- Implement all endpoints above, including the public booking-link flow.
- Create relational models for partners, properties, property photos, guests, reservations, booking links, payments, and settings.
- Add indexes for common filters such as partnerId, status, checkIn, checkOut, and guest/property relationships.
- Enforce ownership and authorization on every partner-scoped endpoint.
- Do not expose partner-private data from public booking endpoints.
- Keep payment integration out of scope; record payment preferences/status only, and clearly mark payment records as demo data unless a real provider is configured.
- Add OpenAPI/Swagger documentation with request/response schemas and enums.
- Seed the demo data needed to exercise the frontend.
- Add tests for authentication, validation, ownership, CRUD, status transitions, date/price calculation, photo handling, and public booking submission.
- At completion, report how to run the API, apply migrations, seed data, view API docs, and run tests. Include any assumptions or incomplete integrations.
